# 1054：数据库少了一列，全服登录崩了一上午——一次 schema 漂移事故复盘

上午十点，测试服突然进不去游戏了。

不是卡，不是慢，是所有登录请求全部报错。日志里一条接一条刷着同一个东西：

```
Error 1054 (42S22): Unknown column 'rename_times' in 'field list'
```

这是我在游戏服务端项目里最难忘的一次事故——因为它根本不是 bug，是**代码和数据库各走各的路**。

## 一、事故现场：一条 SQL 引发的全服雪崩

事情的起因很简单：前一天我们给玩家改名功能加了个计数，代码里给角色表新增了一列 `rename_times`（本文所有字段名均为示意），业务逻辑写完、测试通过、合并、部署。

第二天测试服一开，登录链路全挂。

复盘的时候发现雪崩链是这样的：

1. 登录时服务端会执行一条 `SELECT` 全列查询，把玩家的角色数据读出来
2. 新代码的查询语句里带着 `rename_times` 这个字段
3. 但测试服的数据库**从来没有执行过加这一列的 DDL**
4. MySQL 不认识这个字段 → 直接报 1054
5. 登录是游戏的一切入口 → 登录挂 = 所有功能挂
6. 雪上加霜：请求大量失败触发了服务端的熔断器，连本来能成功的请求也被拦了

**一行没执行的 ALTER，干掉了整个测试环境。**

## 二、根因：schema 漂移，代码和数据库的版本分离

问题的本质，是开发流程里一个特别容易忽略的裂缝：

**代码的版本管理是 git，数据库的版本管理……靠人肉。**

- 开发人员改了代码，顺手在本地库执行了 `ALTER TABLE`，本地一切正常
- 提交代码时，`.sql` 建表脚本也跟着改了
- 但部署流程里，**没有任何一步保证"数据库结构"和"代码版本"是同步的**

于是代码和库的版本差，就静默地躺在那里，等下一次部署时引爆。我们把这种状态叫 **schema 漂移**——它平时不显形，只在某个查询真正碰到那个不存在的字段时炸出来。

而且漂移的方向不止"库少了列"这一种：改了列名没同步、删了字段代码还在查、类型改了没迁移——全是同一个家族。

## 三、我们踩过的四个变体：这不是一次事故，是一类事故

后来我把项目里所有 1054 的案底翻了一遍，发现这家人丁兴旺：

| # | 缺失的列 | 影响 | 发现方式 |
|---|---|---|---|
| 1 | 角色表的改名计数字段 | 登录链路全挂 + 熔断器打开 | 全服报错，炸得最响 |
| 2 | 角色表的兑换累计字段 | 登录取角色列表直接失败 | 同样登录挂，1054 再次光顾 |
| 3 | 玩法统计表的三个新增列 | 获取角色信息接口报错 | 合并新代码后立刻触发 |
| 4 | 打点表的五个新增字段 | 经济数据落库失败 | **没人发现**，直到我主动核对 schema 才揪出来 |

注意第 4 行——它才是这四个里最危险的一个。因为打点写入走的是"旁路"逻辑：**失败只记一条日志，不阻断业务流程**。玩家照常玩、钱照常算，但经济数据一条都没落库。如果没人主动去对账，它可以静默漂移几个月，而基于错误数据做的运营决策，错得悄无声息。

**会爆炸的错误不可怕，静默的错误才可怕。** 前三个损失的是可用性，第 4 个损失的是判断力。

## 四、排查方法论：1054 三板斧

踩了这么多次之后，我们总结出了一套标准排查流程：

**第一板斧：定位缺失列。** 1054 的报错信息会直接告诉你缺的是哪一列。但注意：如果一条 INSERT 同时缺多列，**1054 只报列顺序里的第一个缺失列**——补完一个再跑，下一个才会冒出来。别指望一次报完。

**第二板斧：去 `.sql` 里找定义。** 仓库里的建表脚本是最新的权威定义，找到那一列的类型、默认值、注释，照着补。

**第三板斧：只补缺失的这一列。** 这是最容易犯的错——图省事照着 `.sql` 全量补，结果撞上 `Error 1060: Duplicate column name`。因为有的列其实早就补过了，只是记录没跟上。正确的姿势是**先 `SHOW COLUMNS` 看现状，缺什么补什么**。

一套下来几分钟，但每次都省掉半天的瞎猜。

## 五、预防体系：让 schema 漂移变成可控事件

修 bug 只能解决这一次，我们后来建立的是三道防线：

1. **DDL 变更必须记入版本文件**：项目里维护一个 `db_history.md`，每次改表结构，按版本号记录一行。部署前对着它逐条核对目标环境的 schema——这条文件，就是数据库的"git log"
2. **部署前强制核对**：把"目标库 schema 是否包含本次版本的所有 DDL"写成部署清单里的固定一项，和构建、推送并列
3. **定期对账**：写个小工具解析仓库里所有 `.sql` 的建表语句，逐表逐列 diff 线上库的 `information_schema`——一次跑完，所有静默漂移（像第 4 行那种）全部现形

心态上还有一条更重要的：**把 schema 漂移当成常态，而不是意外。** 只要团队还在加功能、还在合并代码，漂移就一定会再次发生。防是防不住的，能做的是让它每次发生都"炸得早、修得快、记得住"。

## 结尾

那次事故之后，我们项目的 1054 从"每次部署提心吊胆"，变成了"排查手册上的一条标准流程"。事故没有消失，但它从灾难降级成了例行公事。

如果这篇文章让你想起自己项目里的某个"没执行的 ALTER"——现在就去把它查出来，别等它炸。
